# Threat model

Method: STRIDE per trust boundary. Revisit on every major architecture change (new protocol, IPC, plugin host, update channel).
Version 1, 2026-11-01; status column reviewed 2026-11-05 against the source (Codex X02/X03); 2026-11-12: plugin boundary added (design only); 2026-11-14: plugin amendment 1 folded in (T18.21–T18.28; T18.1–T18.5, T18.8, T18.9, T18.12, T18.13, T18.15, T18.18–T18.20 and T21 changed); 2026-11-16: T28 dynamic folders added (B15 review, design only). Source presence is not a per-platform test result: those live in `AUDIT.md`.

## Assets
Saved credentials (passwords, SSH keys, API tokens) · vault master password / OS-keychain-wrapped key · connection inventory (reveals customer topology) · live sessions and tunnels · hypervisor console tickets · audit log · release-signing keys.

## Trust boundaries
1. **User ↔ app process.** Same OS user; the app cannot defend against a fully compromised user session.
2. **App ↔ disk.** Documents, vault, backups, audit log. Plugin data in documents (planned): T18.28; plugin storage and log files: T18.21.
3. **App ↔ remote endpoints.** SSH servers, jump hosts, RDP/VNC, hypervisor APIs, Vaultwarden.
4. **Shell/CLI/WSL ↔ app** via local IPC (macOS implemented 2026-11-03; a Windows named-pipe server exists in core, `core/src/ipc.rs`).
5. **App ↔ plugins** (planned; design in `docs/specs/plugins.md`, agreed by the owner on 2026-11-12; no code yet). A plugin is a WebAssembly component that runs in a helper process, one per plugin and entry with open views. The helper runs in an OS sandbox with no network and no file access apart from its own read-only files (macOS sandbox profile; Windows AppContainer and job object). It talks to the core only over two pipe handles that reach only the helper. The core checks the user's permission grant and policy on every call and writes the audit record. Threats: T18 and T18.1–T18.28 under "Plugin threats".
6. **Build/release pipeline ↔ users** (updates, planned). The plugin catalogue is a second signed channel on the same pattern, with its own keys: T18.10–T18.14. Plugin builds: T18.9, T18.11.
7. **Customer A data ↔ customer B data** (logical, not cryptographic). Plugins get credentials only through a release function that applies the customer-scope check: T18.7. Plugin storage is split per entry, which stops one customer's data from reaching another customer's server: T18.8.

| T28.2 | A trusted task is changed later in the shared document | T/E | Any change to program, args, run_on or timeout changes the hash and drops trust | Planned |
| T28.3 | Shell or argument injection, or PATH planting | E | No shell (`tasks::run_local`); no `$...$` substitution; only `Custom` + `run_on: Local`; absolute program path checked at trust and run time | Planned |
